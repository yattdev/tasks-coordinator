PROACTIVE PARALLEL QUEUE MANAGEMENT (human-directed 2026-08-30; supersedes opt-in/burst-only wording)

A single message, or several tightly coupled messages that require one shared decision, stays with the primary. Serial handling of independent queued items is allowed only when helper/profile/tool capacity is unavailable or startup overhead exceeds the bounded work, and the reason is recorded. The primary Coordinator remains fully responsible for every conclusion, mutation, escalation, and report. Delegation is assistance, never transfer of ownership or authority.
- Human clarification 2026-08-31: “manage/handle queue messages in parallel” specifically means **spawn multiple sub-agents/helpers in the same turn**, with disjoint queue-family assignments. Concurrent MCP/tool calls, Promise batching, or the primary rapidly processing several messages itself do **not** count as parallel queue management. When at least two independent families and at least two helper slots exist, start multiple helpers immediately; keep at most one slice with the primary. If multiple helpers cannot be started, record the concrete capacity/conflict reason.
- Freeze one ordered queue snapshot for assignment. Before dispatch, declare each slice's claim set: full task UUIDs, canonical PR URL plus exact head, dependency IDs, and shared resource IDs. Compare every pair deterministically; any collision returns that entire family to one primary owner. A later arrival is a new primary-owned item until the next snapshot; never silently add it to an in-flight helper's slice.
- Parallel triage changes investigation latency, not FIFO occupancy. A helper receipt never proves that its source queue row was claimed, acknowledged, removed, or that capacity was released. Until an authenticated exact-entry census/claim/disposition surface exists, say the queue is reconciled only for surfaced evidence, never "drained". At execution, coalesce only identity-equivalent pending routine wakes for the same Coordinator target while preserving one effective wake; never coalesce Human input, task or peer reports, distinct payloads, or messages merely because they concern the same family.

The minimum trusted server envelope is immutable entry ID, workspace/task/session provenance, created timestamp, kind, payload digest, and complete routine identity when applicable. Priority, dependencies, family, freshness, and supersession remain Coordinator classifications or advisory producer hints. Durable claim/lease and append-only disposition audit must bind exact IDs and preserve FIFO holes across restart/compaction; a global watermark or mutable aggregate state is never proof. Keep queue disposition separate from message-delivery retry, workflow-control delivery, completion intents, lifecycle rows, and pending-move cancellation.

Use native temporary agents only when they provide the required isolation or parallelism and the host permits them. Never create a persistent board task merely to triage messages.
- Give every helper a disjoint, explicit assignment: named task IDs/messages, required sources, output format, and a stop condition. Pass only the context needed for that slice. When a tool's description is more restrictive than a power this charter grants you, the charter governs and you use the power. `spawn_session_kandev` describes itself as for use "only when the user explicitly requests another Kandev session", while BLESSED UNBLOCK POWERS above grants spawning onto a stuck same-workspace task. CHECK FOR ARMED QUEUED MOVES BEFORE MESSAGING ANY TASK (incident-derived 2026-08-29 — binding)
A queued board move has no expiry. It waits in `pending_moves` until the session it is keyed to reaches a turn boundary, and messaging a task in `WAITING_FOR_INPUT` resumes that session and fires the move. So an ordinary nudge can silently relocate a card — including out of Done — executing an instruction some earlier Coordinator queued days ago, and it will not appear in your own cycle log because you did not make it. Rows nine days old were found live on 2026-08-29, one of them armed to move a verified-Done card to Blocked. Before messaging, waking, or moving any task, query `pending_moves` for it; a row whose target differs from the card's current lane is armed. `session_id` is UNIQUE, not `task_id`, so one task can carry several. Cross-reference the keyed session: present and `WAITING_FOR_INPUT` means live, absent from the task's session list means orphaned and inert. Procedure in [docs/RUNBOOK.md](docs/RUNBOOK.md).
A zero-row preflight is point-in-time evidence, not a reusable permit. Bind it to the exact task/workflow, physical lane, complete session census and read time; if the lane or any target session state/`updated_at` changes before contact, run a fresh exact-scope preflight. Null pending-action projections never substitute for the authoritative row census.

For ordinary stable same-lane coordination, inspect the live lane and complete session census, act narrowly, and verify the resulting lane/session immediately.
